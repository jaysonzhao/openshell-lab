= Module 2: Policy and Security
:navtitle: Policy and Security

This is the core OpenShell exercise. An agent with a shell and network access
needs controls that live outside the model — and a customer must be able to
*prove* what the agent could and could not reach, not just assert it. You will
observe default-deny egress (egress is outbound network traffic), apply the
repository's read-only GitHub policy, prove that reads succeed while writes
remain blocked by L7 enforcement (L7 is the HTTP layer, where a proxy can see
the actual request — method, path, body — not just the destination), and
inspect the audit evidence. The important lesson is not just that OpenShell
denies; it is that the policy decision is visible, specific, and testable
without restarting the sandbox. That is the evidence a compliance review or
customer security conversation actually asks for.

== Technical context

A policy file is desired state, not proof of enforcement. Each exercise compares
the effective policy, the observed request result, and the corresponding gateway
event. Network policy changes are applied without recreating the sandbox;
filesystem policy is verified in a separate sandbox because Landlock is applied
at sandbox startup.

Landlock is the mechanism behind the filesystem boundary: a Linux kernel
security feature where a process declares which filesystem paths it may
access, and the kernel enforces that declaration. A process can narrow its own
access but never broaden it. Unlike the network boundary, there is no proxy in
between — the kernel itself does the enforcing.

== Learning objectives

* Identify the default filesystem and network boundary.
* Observe a denied network request and its log evidence.
* Apply a read-only L7 policy without recreating the sandbox.
* Verify that an allowed GET succeeds while a POST remains blocked.
* Verify mandatory Landlock behavior with positive and negative controls.

== Establish the test context

Run this module in the terminal from the `rhai-agent-security` repository
root. Select the local gateway explicitly so the commands cannot operate on the
SAW gateway:

[source,bash,role="execute",subs="attributes+"]
----
test -f {automation_repo}/policies/sandbox-policy-quickstart.yaml

Expected result: the status reports the selected local gateway and the sandbox
lookup succeeds, confirming the Module 1 environment is intact.

What each command establishes:

* the two `test -f` commands verify the policy files exist in the checkout
  before any policy is applied;

  a SAW gateway;
* `sandbox get ... >/dev/null` confirms the Module 1 sandbox still exists —
  its output is discarded because only the success exit code matters.

== Exercise 1: Observe default deny

How enforcement works here, in two sentences: network traffic from the sandbox
passes through a proxy at the gateway that checks every request against your
policy, and the kernel itself guards file access with no proxy in between.
This exercise watches the first half; Exercise 5 tests the second.

The new sandbox starts with default-deny network policy. Its filesystem policy
still permits the normal work paths such as `/sandbox` and `/tmp`; this module
focuses on the network boundary.

Inspect the effective policy first:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} policy get {raw_sandbox_name} --full
----

Expected result: no network allow rules — the policy declares default-deny
egress while permitting the normal work paths. This is the desired state you
are about to test against reality.

Now attempt an undeclared destination from inside the sandbox:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
  curl -fsS --connect-timeout 10 --max-time 30 https://api.github.com/zen
----

Expected result: the request fails before any HTTP response. `sandbox exec`
exits non-zero, and `curl` reports a connection failure — the network boundary
denied the destination.

Verify the denial produced audit evidence. The sandbox flushes runtime events
to the gateway asynchronously, so the evidence query follows a short wait:

[source,bash,role="execute",subs="attributes+"]
----
sleep 6
openshell --gateway {raw_gateway_name} logs {raw_sandbox_name} --since 30s
----

Expected result: an OCSF event (OCSF is a standard format for security-event
logs) naming `api.github.com`, the calling binary
(`/usr/bin/curl`), and the denial reason. Those three fields are the audit
evidence: the event answers *what was attempted*, *by what*, and *why it was
refused* — exactly what a reviewer needs. A request that fails with no matching
event means the failure was local, not a policy denial.

In the TUI, the same DENIED event appears in real time as you run the request —
sandbox identity, binary, destination, and denial reason. Same evidence as the
log query, live.

.The scripted assertion for this exercise
[%collapsible]
====
[source,bash,subs="attributes+"]
----
REQUEST_DENIED=false
if openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
  curl -fsS --connect-timeout 10 --max-time 30 https://api.github.com/zen; then
  echo 'ERROR: the default policy allowed egress'
else
  REQUEST_DENIED=true
  echo 'The request failed; verify the gateway denial record next.'
fi
sleep 6
DENIAL_LOG=$(openshell --gateway {raw_gateway_name} logs {raw_sandbox_name} --since 30s)
printf '%s\n' "$DENIAL_LOG"
EVIDENCE_FOUND=false
if printf '%s\n' "$DENIAL_LOG" | \
  grep -Ei 'api\.github\.com' | grep -Eiq 'deny|denied|blocked'; then
  EVIDENCE_FOUND=true
else
  echo 'ERROR: no api.github.com gateway-denial evidence was found'
fi
test "$REQUEST_DENIED" = true && test "$EVIDENCE_FOUND" = true
----
====

== Exercise 2: Apply the read-only policy

Apply the workshop's bundled copy of the OpenShell read-only policy:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} policy set {raw_sandbox_name} \
  --policy {automation_repo}/policies/sandbox-policy-quickstart.yaml \
  --wait
openshell --gateway {raw_gateway_name} policy get {raw_sandbox_name} --full
----

Expected result: the effective policy now shows a read-only REST rule scoped to
`/usr/bin/curl` for `api.github.com`, without recreating the sandbox.

An allow rule has multiple dimensions:
destination, protocol, HTTP access mode, and calling binary. That last one is
*binary binding*: the grant goes to a specific program, not to the sandbox as
a whole. A hostname alone is not the capability grant — reading the effective
rule line by line is how you explain a capability to a reviewer.

Run an allowed GitHub API read with the granted binary:

[source,bash,role="execute",subs="attributes+"]
----
STATUS=$(openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
  curl -sS --connect-timeout 10 --max-time 30 \
  -o /dev/null -w '%\{http_code\}' \
  https://api.github.com/repos/NVIDIA/OpenShell)
printf 'GitHub API HTTP %s\n' "$STATUS"
----

Expected result: HTTP 200. GET, HEAD, and OPTIONS are allowed by the read-only
preset. GitHub rate-limits unauthenticated requests to 60 per hour per source
IP, so a classroom behind one shared address can exhaust that limit; a 403
with `X-RateLimit-Remaining: 0` is an upstream rate limit and still proves the
proxy allowed the connection. A 403 without those headers is a policy denial;
the gateway events distinguish the two. This is HTTP-method enforcement; it
cannot guarantee that every GET endpoint is semantically free of side effects.

.Diagnosis for the shared-IP 403 case
[%collapsible]
====
[source,bash,subs="attributes+"]
----
if [ "$STATUS" = "403" ]; then
  RATE_LIMIT=$(openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
    curl -sI --connect-timeout 10 --max-time 30 \
    https://api.github.com/repos/NVIDIA/OpenShell | grep -i 'x-ratelimit-remaining: 0' || true)
  if [ -n "$RATE_LIMIT" ]; then
    echo 'PASS WITH NOTE: the proxy allowed the request; GitHub exhausted the shared unauthenticated rate limit (X-RateLimit-Remaining: 0)'
  else
    echo 'FAIL: a 403 without rate-limit headers may be a policy denial; check the gateway events'
    openshell --gateway {raw_gateway_name} logs {raw_sandbox_name} --since 2m
    test "$STATUS" = "200"
  fi
fi
----
====

Now the negative control: repeat the same read with a binary that is not listed
in the rule. The capability was granted to `/usr/bin/curl`, not to the sandbox:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} sandbox exec \
  -n {raw_sandbox_name} -- \
  python3 -c "import urllib.request; urllib.request.urlopen('https://api.github.com/zen', timeout=10)"
----

Expected result: the request fails. Binary binding rejected `python3` even
though the host is allowed — the grant is scoped to the calling binary.

.Evidence check for the binary denial
[%collapsible]
====
[source,bash,subs="attributes+"]
----
sleep 6
DENIAL_LOG=$(openshell --gateway {raw_gateway_name} logs \
  {raw_sandbox_name} --level info --since 30s)
printf '%s\n' "$DENIAL_LOG"
printf '%s\n' "$DENIAL_LOG" | grep -Ei 'api\.github\.com' | \
  grep -Eiq 'deny|denied|blocked'
----
====

== Exercise 3: Prove L7 blocking

Attempt a write to the GitHub API with the same allowed host and binary:

[source,bash,role="execute",subs="attributes+"]
----
POST_STATUS=$(openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
  curl -sS --connect-timeout 10 --max-time 30 \
  -X POST -o /dev/null -w '%\{http_code\}' \
  https://api.github.com/repos/octocat/hello-world/issues \
  -H 'Content-Type: application/json' -d '{"title":"blocked-by-policy"}' || true)
printf 'POST result: HTTP %s\n' "$POST_STATUS"
----

Then inspect the policy evidence:

[source,bash,role="execute",subs="attributes+"]
----
sleep 6
openshell --gateway {raw_gateway_name} logs {raw_sandbox_name} --level info --since 30s
----

The CONNECT is permitted because `api.github.com` is an allowed host, but the
L7 proxy blocks the HTTP method. Look for the sandbox identity, `POST`, target
path, and denial reason in the OpenShell log. The HTTP status alone is not proof
of policy enforcement: an unauthenticated write can also receive an upstream
GitHub `4xx` response. The OpenShell denial event is the required evidence.

.The scripted assertion for this exercise
[%collapsible]
====
[source,bash,subs="attributes+"]
----
DENIAL_LOG=$(openshell --gateway {raw_gateway_name} logs {raw_sandbox_name} --level info --since 30s)
printf '%s\n' "$DENIAL_LOG" | grep -Ei 'api\.github\.com' | \
  grep -Ei 'POST' | grep -Eiq 'deny|denied|blocked'
----
====

The sandbox can reach the approved service, but the policy rejects a POST from
the same binary to that host.

== Exercise 4: Change and restore a live rule

This exercise is the operational loop a platform admin actually runs when a
developer requests access: review a narrowly scoped change, apply it live while
the workload keeps running, verify the result, then restore known-good state.

Use a precise live update to add a temporary read-write REST endpoint while the
sandbox remains running. The target is the in-cluster `http-echo` service the
raw OpenShell environment deploys — the tiny echo-back service from Module 1 —
so no external host is required:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} policy update {raw_sandbox_name} \
  --add-endpoint http-echo.{openshell_namespace}.svc.cluster.local:8080:read-write:rest:enforce \
  --binary /usr/bin/curl \
  --wait
openshell --gateway {raw_gateway_name} policy get {raw_sandbox_name} --full
----

Reading the `--add-endpoint` value: `host:port:access-mode:protocol:enforcement`
— a single endpoint grant scoped to one binary and one access mode. The
effective policy now shows the new endpoint. In the TUI, an ALLOWED event for
`http-echo` appears once the POST succeeds below.

Run a harmless POST against the temporary endpoint:

[source,bash,role="execute",subs="attributes+"]
----
STATUS=$(openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
  curl -sS --connect-timeout 10 --max-time 30 \
  -X POST -o /dev/null -w '%\{http_code\}' \
  "http://http-echo.{openshell_namespace}.svc.cluster.local:8080/post" \
  -d 'policy=updated')
printf 'http-echo HTTP %s\n' "$STATUS"
----

Expected result: HTTP 200. No sandbox recreation was required — network policy
hot-reloads.

Restore the canonical read-only policy and prove the temporary endpoint is
removed:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} policy set {raw_sandbox_name} \
  --policy {automation_repo}/policies/sandbox-policy-quickstart.yaml \
  --wait
openshell --gateway {raw_gateway_name} policy get {raw_sandbox_name} --full
----

Expected result: the effective policy no longer contains `http-echo`.

Repeat the POST and confirm the denial returned:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
  curl -fsS --connect-timeout 10 --max-time 30 \
  -X POST "http://http-echo.{openshell_namespace}.svc.cluster.local:8080/post" \
  -d 'policy=reverted'
----

Expected result: the request does not complete. Verify the denial event:

[source,bash,role="execute",subs="attributes+"]
----
sleep 6
openshell --gateway {raw_gateway_name} logs {raw_sandbox_name} --level info --since 30s
----

In the TUI, the DENIED event for `http-echo` reappears after the restore — the
event stream flips ALLOWED back to DENIED in real time as policy changes. This
is the strongest moment to show on screen in a customer demo.

Confirm that the full policy no longer contains `http-echo` and that the log
records a denial for that destination. Those two observations distinguish a
policy denial from an unrelated upstream failure.

.The scripted assertion for the restore
[%collapsible]
====
[source,bash,subs="attributes+"]
----
REVERT_DENIED=false
if openshell --gateway {raw_gateway_name} sandbox exec -n {raw_sandbox_name} -- \
  curl -fsS --connect-timeout 10 --max-time 30 \
  -X POST "http://http-echo.{openshell_namespace}.svc.cluster.local:8080/post" \
  -d 'policy=reverted'; then
  echo 'ERROR: the reverted policy still allows http-echo'
else
  REVERT_DENIED=true
  echo 'Request did not complete; verify the OpenShell denial event next.'
fi
sleep 6
DENIAL_LOG=$(openshell --gateway {raw_gateway_name} logs {raw_sandbox_name} --level info --since 30s)
printf '%s\n' "$DENIAL_LOG"
EVIDENCE_FOUND=false
if printf '%s\n' "$DENIAL_LOG" | grep -Ei 'http-echo' | \
  grep -Eiq 'deny|denied|blocked'; then
  EVIDENCE_FOUND=true
fi
test "$REVERT_DENIED" = true && test "$EVIDENCE_FOUND" = true
----
====

A policy change that cannot be reverted is not a policy change: always close
the loop. Network policies hot-reload; filesystem and process policies are
static for a sandbox and require recreation when they change.

== Control layers and evidence

[cols="1,3",options="header"]
|===
| Layer | Evidence to verify

| Network default-deny
| A request to an undeclared host fails and the gateway records a destination-
  specific denial.

| L7 method control
| A GET succeeds while a POST to the same host and binary produces an L7 denial.

| Binary binding
| The effective rule identifies `/usr/bin/curl`; repeat the request with another
  binary before claiming binary binding.

| Landlock filesystem
| A sandbox created with `hard_requirement` starts successfully, allows a write
  to `/tmp`, and denies a write to otherwise writable `/var/tmp`.
|===

== Exercise 5: Verify mandatory Landlock enforcement

Landlock requires Linux 5.13 or later. Verify the node kernels before creating
the `hard_requirement` sandbox; a failure here is a node capability limit, not
a policy problem:

[source,bash,role="execute",subs="attributes+"]
----
LOWEST_KERNEL=$(oc get nodes -o jsonpath='{range .items[*]}{.status.nodeInfo.kernelVersion}{"\n"}\{end\}' | sort -V | head -1)
printf 'Lowest node kernel: %s\n' "$LOWEST_KERNEL"
if [ "$(printf '%s\n5.13\n' "$LOWEST_KERNEL" | sort -V | head -1)" = "5.13" ]; then
  echo 'EXPECTED: all nodes meet the Landlock kernel requirement (>= 5.13)'
else
  echo 'WARNING: a node kernel is older than 5.13; hard_requirement cannot start'
fi
----

Filesystem policy is static for a running sandbox. Create a separate sandbox
whose startup must fail if Landlock cannot enforce the declared paths —
`hard_requirement` means the sandbox refuses to start rather than running
without the filesystem boundary:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} sandbox delete landlock-proof 2>/dev/null || true
openshell --gateway {raw_gateway_name} sandbox create \
  --name landlock-proof --no-auto-providers \
  --policy {automation_repo}/policies/sandbox-policy-landlock-hard.yaml \
  --no-tty -- true
----

.Readiness wait for the hard-requirement sandbox
[%collapsible]
====
[source,bash,subs="attributes+"]
----
LANDLOCK_READY=false
for i in $(seq 1 30); do
  if openshell --gateway {raw_gateway_name} sandbox exec \
    -n landlock-proof -- true >/dev/null 2>&1; then
    LANDLOCK_READY=true
    break
  fi
  sleep 5
done
if [ "$LANDLOCK_READY" != true ]; then
  echo 'ERROR: hard-requirement sandbox did not become Ready; inspect Landlock availability'
else
  echo 'Sandbox started; Landlock availability was sufficient for startup'
fi
----
====

Expected result: the sandbox starts — the node kernel supports Landlock.

Run the positive control. A write inside the allowlist must succeed:

[source,bash,role="execute",subs="attributes+"]
----
POSITIVE_CONTROL=false
LANDLOCK_DENIED=false
openshell --gateway {raw_gateway_name} sandbox exec -n landlock-proof -- \
  sh -c 'touch /tmp/allowed && rm /tmp/allowed' && POSITIVE_CONTROL=true
----

Expected result: the command succeeds. This proves the sandbox can write
normally inside the declared paths.

Run the negative control. A write outside the allowlist must fail:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} sandbox exec -n landlock-proof -- \
  touch /var/tmp/openshell-workshop-probe || LANDLOCK_DENIED=true
----

Expected result: the command fails with a permission error — Landlock denied
the path that ordinary permissions allow.

Inspect the logs and remove the proof sandbox:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {raw_gateway_name} logs landlock-proof --since 2m
openshell --gateway {raw_gateway_name} sandbox delete landlock-proof
test "$LANDLOCK_READY" = true && test "$POSITIVE_CONTROL" = true && \
  test "$LANDLOCK_DENIED" = true
----

If sandbox creation fails, inspect the reported Landlock availability instead
of weakening the policy. The successful `/tmp` control distinguishes a general
write failure from the denied path test.

Attribute the denied write to Landlock, not to ordinary permissions, by
checking both sides: the probed directory is world-writable (mode 1777), so
plain permissions cannot deny the sandbox user there, and the allowed-path
control succeeds. Unlike network denials, which the enforcement proxy records
as `NET:OPEN DENIED` runtime events, Landlock filesystem denials are
kernel-silent — the kernel returns EACCES with no notification, so no runtime
event appears in `openshell logs`. The failing `touch` itself is the evidence.

== Optional: Run the automated control-layer test

The repository ships an automated test that verifies every control layer
against the running sandbox in one pass. Run it from the
`rhai-agent-security` repository root after restoring the canonical policy:

[source,bash,role="execute",subs="attributes+"]
----
openshell gateway select {raw_gateway_name}
make -C {automation_repo} openshell-security-test SANDBOX_NAME={raw_sandbox_name}
----

Each control prints `[ALLOWED]` or `[BLOCKED]` with the observed HTTP status or
file result. The allowed GitHub read and the `/sandbox` and `/tmp` writes must
print `[ALLOWED]`, every denied control must print `[BLOCKED]`, and the process
check must report the unprivileged `sandbox` user. The script exits non-zero
when any control produced unexpected evidence — read the failing line to see
which control layer disagreed with the expected result.

== Exercise 6: Act as the platform admin

The exercises so far viewed evidence from inside one sandbox. Act as the
platform admin and inspect what the gateway recorded across the environment.
The gateway pod log aggregates every RPC from every sandbox, and the Agent
Sandbox API is cluster-scoped:

[source,bash,role="execute",subs="attributes+"]
----
oc get sandboxes -A
oc -n {openshell_namespace} logs statefulset/openshell --tail=500 | \
  grep -oE 'openshell\.[A-Za-z0-9.]+/[A-Za-z]+' | sort | uniq -c | sort -rn
----

Expected result: the sandbox list shows every sandbox in the cluster, and the
RPC summary counts gateway activity by method — typically `CreateSandbox`,
`ExecSandbox`, `RelayStream`, and `SubmitPolicyAnalysis` dominate. This is the
operator's answer to "what did every agent attempt against the gateway?" from
one vantage point, not just one sandbox.

Pass condition: you can see every sandbox in the cluster and the gateway RPC
activity by method — sandbox creation, exec relays, policy analysis — across the
whole environment, not just one sandbox.

For the live operator view of individual decisions, use the TUI you opened at
the start of this module. Terminal 1 runs the commands; Terminal 2 streams the
events as they happen — user-level interaction and operator management side by
side. Reproduce each earlier control layer while watching the event stream:

* default-deny curl (Exercise 1) — the DENIED event for `api.github.com`;
* unbound-binary python3 read (Exercise 2) — the binary-binding denial;
* L7 POST to GitHub (Exercise 3) — the method denial;
* `http-echo` allow, restore, deny (Exercise 4) — ALLOWED flipping back to
  DENIED.

Each event appears with the sandbox identity, binary, destination, and denial
reason. This live view is the demo moment: customers see the policy decision
surface in real time instead of being told about it. The OpenClaw Control UI in
Module 5 is the same pattern at the user layer — browser chat and tool activity
alongside CLI evidence; this TUI is the operator-layer equivalent.

Interpretation notes:

* Denial history is per-sandbox: `openshell logs {raw_sandbox_name}` queries the
  gateway event store for one sandbox. This build has no cross-sandbox denial
  query.
* The gateway pod log shows aggregate RPC activity, and the metrics endpoint
  counts requests by method only. Attribution of an individual denial comes from
  the sandbox OCSF event, not the pod log.

== Evidence checkpoint

The proof sequence is:

. Default-deny egress fails and produces audit evidence.
. A reviewed read-only policy allows GitHub reads.
. L7 enforcement blocks a GitHub POST even though the host is allowed.
. A live policy update allows a temporary test endpoint, then restoration
   removes it.
. A `hard_requirement` sandbox proves whether Landlock is available and enforcing
   the tested path boundary.
. The automated control-layer test exits zero with every control in the
    expected state.
. Acting as platform admin, the cluster-wide sandbox list and the gateway RPC
   summary show what every sandbox attempted against the gateway.

.Answer key
[%collapsible]
====
* Step 1: the request to the undeclared host fails and the gateway records a
   destination-specific denial naming the host and calling binary.
* Step 2: `policy get --full` shows the `read-only` GitHub rule bound to
   `/usr/bin/curl`; the GET returns HTTP 200.
* Step 3: the POST produces an L7 denial naming the method even though the host
   is allowed; an upstream GitHub 4xx is not acceptable evidence.
* Step 4: `policy update --add-endpoint` hot-reloads the rule; the POST
   succeeds while the temporary endpoint is active, and the denial returns after
   `policy set` restores the canonical file.
* Step 5: the `hard_requirement` sandbox starts only when the node kernel
   supports Landlock (5.13 or later); the `/tmp` write succeeds and `/var/tmp`
   is denied.
* Step 6: the automated test exits 0 with every control in the expected state.
* Admin step: `oc get sandboxes -A` lists every sandbox cluster-wide, and the
   gateway pod log aggregates RPC activity by method. Individual denial
   attribution stays in the sandbox OCSF event.
====

That is stronger than saying "the agent is safe." It establishes a repeatable,
observable capability boundary: for every action the agent attempted, you can
state what was allowed, what was denied, and where the evidence lives. In a
customer conversation, that distinction is the difference between a security
claim and a demonstrable control.
