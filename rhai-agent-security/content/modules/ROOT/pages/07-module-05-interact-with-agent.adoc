= Module 5: Test Agent Capabilities and Governance
:navtitle: Test Agent Capabilities

Modules 1-2 proved the policy controls on a pod boundary. This module tests
the same boundaries around a model-backed agent in the production VM shape,
with a human driving it from a browser. It covers what a customer needs to
prove: the agent writes only where the policy allows, governance rejects
unapproved provider changes, and every claim can be checked from outside the
agent.

The agent is model-backed and running inside a SAW-provisioned NemoClaw
OpenShell sandbox. In this module you will verify a permitted workspace action,
test a denied filesystem action, inspect runtime evidence, exercise a
governance rejection, and drive the agent from the browser Control UI.

== Technical context

Agent output is not enforcement evidence. Validate each result from outside the
agent by inspecting the workspace, effective policy, and gateway events.

Run the commands from the SAW checkout root against the gateway configured
in Module 4.

== Exercise 1: Verify the permitted workspace action

Confirm again that the file created in Module 4 exists and inspect the effective
filesystem policy:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} -- \
  cat /sandbox/haiku.txt
openshell --gateway {saw_gateway_name} policy get \
  {saw_sandbox} --workspace {saw_workspace} --full
----

The successful write proves that `/sandbox` is usable. It does not by itself
prove that paths outside the allowlist are denied.

== Exercise 2: Test a denied filesystem action

Attempt a write outside the declared workspace:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} -- \
  touch /var/tmp/saw-boundary-probe
----

Expected result: the command fails. The path is outside the Landlock
allowlist — the kernel-level filesystem rule from Module 2 — so the kernel
refuses the write.

.Cleanup for the unexpected-success case
[%collapsible]
====
[source,bash,subs="attributes+"]
----
if openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} -- \
  touch /var/tmp/saw-boundary-probe; then
  echo 'WARNING: the write succeeded; do not claim filesystem enforcement'
  openshell --gateway {saw_gateway_name} sandbox exec \
    -n {saw_sandbox} --workspace {saw_workspace} -- \
    rm -f /var/tmp/saw-boundary-probe
fi
----
====

Then inspect recent events:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} logs {saw_sandbox} \
  --workspace {saw_workspace} --since 2m
----

[IMPORTANT]
====
Attribute the denial to Landlock, not to a Unix permission or SELinux denial:
the probed directory is world-writable (mode 1777), so plain permissions
cannot deny the sandbox user there, and the successful `/sandbox` write from
Exercise 1 confirms the allowlist is what differentiates. Landlock filesystem
denials are kernel-silent — the kernel returns EACCES with no notification, so
the log query above shows only control-plane noise and no denial runtime
event. The failing `touch` itself is the evidence.
====

== Exercise 3: Inspect managed capabilities

The *governance interceptor* is the platform's policy gatekeeper: it sits
between the gateway and sandbox operations, signs each sandbox's policy, and
*vends* — serves up — the provider profiles agents may use. Inspect the
profiles it vends. The authenticated
profile-list operation proves authenticated reads of the governance data work
for your identity:

[source,bash,role="execute",subs="attributes+"]
----
export OPENSHELL_SAW_NAME={saw_gateway_name}
openshell --gateway "$OPENSHELL_SAW_NAME" provider list-profiles
----

The workshop checkout is read-only and the GitHub profile is already present, so
do not run a helper that commits and pushes profile changes. Persistent changes
require a writable fork tracked by Argo CD and a reviewed pull request.

Expected result: the workshop's GitHub profile is listed — authenticated reads
of the governance data work for your identity.

Then test that the interceptor rejects an unvended provider type:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway "$OPENSHELL_SAW_NAME" provider create \
  --name workshop-blocked --type custom --credential key=value
----

Expected result: the request is rejected with an error naming the unvended
type. This verifies fail-closed governance — anything outside the governance
baseline is refused, never silently allowed — for the intercepted
`CreateProvider` operation. It does not imply that every operation in the VM
traverses the interceptor.

.Scripted assertion for the rejection
[%collapsible]
====
[source,bash,subs="attributes+"]
----
if OUTPUT=$(openshell --gateway "$OPENSHELL_SAW_NAME" provider create \
  --name workshop-blocked --type custom --credential key=value 2>&1); then
  echo 'ERROR: custom provider creation unexpectedly succeeded'
  openshell --gateway "$OPENSHELL_SAW_NAME" provider delete workshop-blocked
  false
else
  printf '%s\n' "$OUTPUT"
  echo 'EXPECTED: authenticated request was rejected for an unvended type'
fi
----
====

For lower-level live network activity and approval prompts, use the OpenShell
TUI — as in Module 2, run it in a second terminal and leave it open while you
work, so the operator view streams events while you drive the agent:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} term --workspace {saw_workspace}
----

SAW governance profiles are the managed workflow; `openshell` is the lower-level
inspection and live-approval workflow. The enforceable boundary remains the
OpenShell policy, not an OpenClaw prompt or workspace file.

== Exercise 4: Drive the agent from the browser Control UI

The OpenClaw Control UI is the agent's browser face: chat with the agent,
watch tool activity live, and approve device pairings. The setup job wires
the whole path — it starts the agent's gateway daemon (the agent's background
WebSocket service) inside the sandbox, configures the allowed browser origin
from the dashboard Route (the OpenShift URL that exposes it), and installs
a systemd unit on the gateway VM that forwards `{saw_gateway_name}-dashboard`
route traffic into the sandbox with the gateway's native `openshell forward`
RPC. The daemon binds loopback (listens only on the sandbox's own address), so
the Route only works through that authenticated forward; no manual port
plumbing is involved.

Confirm the daemon is listening inside the sandbox:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} --no-tty -- \
  sh -c 'ss -ltn | grep 18789 || echo "daemon not listening"'
----

Expected result: a listening line on port 18789 — the agent's WebSocket gateway
bound to loopback inside the sandbox (only the sandbox itself can reach it).
`daemon not listening` means the setup
Job's wiring did not finish; fix that before opening the UI.

Then acquire the UI token. The token authenticates the UI session and is a
credential — treat the token-bearing URL like a password. The `openclaw` CLI
redacts the token, so read it from the sandbox config file: the python
one-liner extracts `gateway.auth.token` from `openclaw.json`, the same method
the shipped `openshell-saw-gui.sh` script uses:

[source,bash,role="execute",subs="attributes+"]
----
TOKEN=$(openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} --no-tty -- \
  cat /sandbox/.openclaw/openclaw.json 2>/dev/null \
  | python3 -c "import sys,json; print(json.load(sys.stdin).get('gateway',{}).get('auth',{}).get('token',''))")
test -n "$TOKEN" && echo "token acquired"
----

Expected result: `token acquired`.

Build the browser URL from the dashboard Route:

[source,bash,role="execute",subs="attributes+"]
----
DASHBOARD_URL="https://$(oc get route {saw_gateway_name}-dashboard \
  -n {saw_namespace} -o jsonpath='{.spec.host}')/#token=$TOKEN"
echo "$DASHBOARD_URL"
----

Expected result: the token-bearing URL prints. Open it in a browser. The UI
authenticates from the `#token=`
fragment and lands in the chat session. Verify `Gateway status: Online` in
the sidebar, then interact with the agent: use one of the suggested prompts
(for example `Check system health`) or type your own request, and watch the
assistant work with live tool activity. The prompts and session controls in
the sidebar are the same object model you inspected through the CLI —
sessions, devices, and gateway health are one system seen from two surfaces.
This is the surface to show a customer: the agent working in a governed
sandbox with tool activity visible, next to the CLI evidence that proves the
boundary.

Before trusting the UI, validate the two controls that gate it. First, the
origin allowlist: the gateway only serves the Control UI to the browser
origin configured in `gateway.controlUi.allowedOrigins` — the setup job sets
it from the dashboard Route host:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} -- \
  openclaw config get gateway.controlUi.allowedOrigins
----

The value must be the URL you opened. Opening the UI from any other origin
is rejected — do not widen the allowlist to make a broken path work.

Second, device pairing. OpenClaw device pairing remains enabled. Each
`openclaw` invocation takes roughly a minute on the emulated workspace VM,
so use generous timeouts. `openclaw devices list --json` names pending
devices, but the CLI keeps the device-pairing stream open and does not exit
on its own; observe pairing requests through the gateway log instead:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} -- \
  sh -c 'grep device.pair /tmp/openclaw-gateway.log | tail -5'
----

When the UI reports a pending device, approve only the displayed request ID
with `openclaw devices approve <REQUEST_ID>` through `openshell sandbox
exec`, then reload the page.

Other sandboxes on the same gateway VM are not forwarded — the VM exposes a
single UI port. Use the shipped tunnel for those, with explicit names:

[source,bash,role="execute",subs="attributes+"]
----
SANDBOX_NAME=<name> WORKSPACE=<workspace> GATEWAY_NAME={saw_gateway_name} \
  ./scripts/openshell-saw-gui.sh
----

== Evidence checkpoint

Collect:

* the effective filesystem policy;
* the permitted workspace file;
* the denied-path result — the failing `touch` plus the world-writable-path
  comparison that attributes the denial to Landlock;
* the successful profile listing followed by the rejected provider creation;
* the Control UI showing `Gateway status: Online` with a completed agent
  interaction; and
* the device-pairing evidence from the gateway log (and the approval record,
  if a pairing was exercised).

.Answer key
[%collapsible]
====
* The effective filesystem policy shows the workspace allowlist; `/sandbox` is
  writable and paths outside it are not declared.
* The permitted workspace file exists and is non-empty (`test -s
  /sandbox/haiku.txt`).
* The denied-path write fails with a permission error. Landlock denials are
  kernel-silent — no runtime event exists for filesystem denials — so the
  evidence is the failing command plus the world-writable (mode 1777) path
  comparison; a Unix permission or SELinux denial is not equivalent evidence.
* The profile listing succeeds for the authenticated identity while the
  unvended `custom` provider creation is rejected by the governance
  interceptor (fail-closed).
* The Control UI loads from the dashboard Route with the token fragment, shows
  `Gateway status: Online`, and completes an agent interaction; the origin
  allowlist value matches the URL used.
====
